# Accessibility and localization: audit

Status: audit of `main` at `31dd630` (2026-11-18). Findings and a fix plan,
nothing fixed yet. Covers `ThemeSettingsUI/GTSThemeSettingsEditor.m` (the
editor view), `ThemeSettingsKit/GTSEditorModel.m` (which produces almost all
the text the view shows) and `ThemeSettingsApp/main.m`.

## Localization

**Theme-provided text is already localizable.** A theme's `Title`, `Help`,
enum value titles and `Unset.Help` come from its own
`ThemeSettings.strings` (schema-v1 section 1; see
[theme-authors.md](theme-authors.md) section 6).

**The editor's own text is not.** No call to `NSLocalizedString` (or any
variant) exists anywhere in the project. Roughly:

| File | String literals | User-visible examples |
|---|---|---|
| `GTSEditorModel.m` | ~140 | Apply messages ("Saved. Restart the affected applications…"), "Follow GNOME's light/dark and accent", state lines ("Inherited from all applications"), menu items ("Default (…)", "Automatic (…)"), read-only reasons |
| `GTSThemeSettingsEditor.m` | ~30 | "Apply", "Cancel", "Reload", "Reset", "Settings for: %@" |
| `ThemeSettingsApp/main.m` | ~20 | The Target menu, "Other application…", "AppImage theme information…", window title |
| `GTSDefaultsDomainStore.m` | ~60, some reach the user through `localizedDescription` | "the settings file could not be read…" |

Things to know before wrapping them:

1. **Tests compare English text.** `GTSEditorModelTests`,
   `GTSReadOnlyBackendTests` and `GTSEditorModelAppImageTests` assert on
   message and state strings. Using the English text as the key (as theme
   `.strings` files already do) keeps them passing with no translation
   installed, and keeps tests in English.
2. **The strings live in libraries, not in an app.** `NSLocalizedString`
   looks in the main bundle, which is the *host* application when the
   editor is embedded. The libraries need
   `NSLocalizedStringFromTableInBundle(…, @"ThemeSettings", <library
   bundle>, …)`, with the `.strings` installed as library resources
   (gnustep-make `ThemeSettingsUI_RESOURCE_FILES`, found at run time with
   `+[NSBundle bundleForLibrary:]`). The AppImage, the MSI and the Debian
   packages must then carry those resources. Today they carry none.
3. **Sentences are assembled from pieces** in a few places (for example
   "Settings for: %@ (%@)", "Not saved: %@ changed elsewhere…", and lists
   joined with ", "). Each needs a whole-sentence format string, so that
   translators can reorder.
4. **Fixed widths.** Labels are 170 pt, controls 330 pt and buttons 80 pt
   (`kLabelW`, `kControlW`, button frames). Longer translations (German,
   for example) will be clipped. Wrapped notes use `wrappedHeight()`, which
   estimates; it is fine for English and untested for anything else.

## Accessibility

1. **Screen readers.** GNUstep on Linux has no bridge to AT-SPI: libs-back
   has no accessibility code, so no screen reader can see any GNUstep app.
   libs-gui has the `NSAccessibility` headers but nothing consumes them.
   Accessibility labels would therefore help no one today. Don't add them
   now; recheck if GNUstep gains a bridge.
2. **Fixed font sizes.** State lines and notes are 10 pt and the message is
   11 pt, hard-coded (`label(…, 10, …)`). They ignore the user's
   `NSFontSize` and the theme's sizes, so a user who enlarges the system
   font still gets 10 pt text. Use `+[NSFont smallSystemFontSize]` (state
   lines and notes) and `+[NSFont systemFontSize]` (the message), and size
   `wrappedHeight()` from the font actually used.
3. **Fixed colours.** Secondary text is `grayColor` or `darkGrayColor`.
   This is fine in the standalone app, which always uses the plain GNUstep
   look. **An embedded editor uses the host's theme**, though: in a dark
   theme (Adwaita dark, ThemeDemo, PR #150), dark grey text on a dark
   background has very poor contrast. Use a theme colour instead:
   `disabledControlTextColor`, or `controlTextColor` at a smaller size.
   Screenshot this in ThemeDemo with Adwaita dark before and after.
4. **Keyboard.** Return is Apply. Escape doesn't cancel: `_cancel` has no
   key equivalent. Making Escape cancel is right for the standalone window.
   For an embedded pane it could clash with a host panel's own Escape, so
   make it something the host can turn off. The rows are rebuilt on every
   reload, and nothing sets `nextKeyView`. Tab order is whatever the
   window's automatic key-view loop works out. Test it: Tab should go
   Theme → each row's control → Reset → … → Reload → Cancel → Apply.
5. **State shown by colour alone:** none found. The state is always given
   in words.

## Fix plan

In order of value. Each item is a normal code change with tests and passes
`scripts/ci.sh` before it's pushed.

1. **Font sizes from the system** (accessibility 2). Small and safe; update
   the screenshot check.
2. **Theme colours for secondary text** (accessibility 3). Small, but needs a
   look in an embedded dark host before it's called done.
3. **Escape cancels in the standalone app; check the Tab order**
   (accessibility 4). Add a GUI check to `scripts/screenshots.sh`.
4. **Localization groundwork** (localization 1-3):
   - a `GTSLocalized(key)` macro that looks in the library's own bundle;
   - wrap the strings with the English text as the key;
   - install an empty `English.lproj/ThemeSettings.strings`;
   - packaging carries the resources.

   It's a large diff touching about 250 strings, but each change is
   mechanical. Translations come later, from contributors.
5. **Widths that fit the text** (localization 4). Only worth doing once
   there's a translation to test with.
